# Одновременная работа нескольких пользователей: сценарий JMeter и изоляция транзакций

## Запуск

Нужен запущенный WildFly с приложением (см. `SETUP.md`), Apache JMeter 5.6+ и доступ к БД приложения.

```bash
jmeter -n -t jmeter/is1-concurrency.jmx -Jthreads=10 \
    -Juser.classpath=$HOME/wildfly-31.0.1.Final/modules/system/layers/base/org/postgresql/main/postgresql.jar \
    -l results.jtl
python3 jmeter/summary.py results.jtl      # сводка по запросам и проваленным проверкам
```

Параметры: `-Jthreads` — число одновременных пользователей (по умолчанию 10), `-Jloops` — число
циклов в группе 1 (3), `-Jhost` / `-Jport` — адрес сервера (`localhost:8080`).
Сценарий сам делает двух пользователей администраторами (роль выдаётся только в БД, через API её
получить нельзя), поэтому ему нужен JDBC-драйвер PostgreSQL (`-Juser.classpath`, копировать драйвер
в JMeter не нужно) и параметры БД: `-JdbUrl` (по умолчанию `jdbc:postgresql://localhost:55432/studs`),
`-JdbUser` (`is1`), `-JdbPassword` (`is1pass`). Для БД на helios — через туннель
`ssh -p 2222 -L 55432:pg:5432 s467604@helios.se.ifmo.ru` и `-JdbUser=s467604 -JdbPassword=…`.

Все имена и координаты в сценарии уникальны для каждого прогона, поэтому сценарий можно
запускать повторно на той же БД. Файл также открывается в GUI JMeter (`jmeter -t ...`).

## Что проверяет сценарий

Группы потоков выполняются по очереди. Внутри группы все потоки стартуют одновременно
(Synchronizing Timer), так что запросы действительно пересекаются по времени.

| Группа | Что делают потоки | Корректное поведение |
|---|---|---|
| 0. Подготовка | регистрирует владельца и двух пользователей, назначает им роль ADMIN (JDBC), проверяет, что роль действует; владелец создаёт три общих объекта | — |
| 1. Обычная работа | каждый пользователь создаёт, изменяет, удаляет свои объекты и импортирует файл | все операции успешны |
| 2. Уникальность имени | N пользователей одновременно создают объект с одним именем | ровно один 201, остальные 409; в БД один объект |
| 3. Уникальность координат | N пользователей одновременно создают одинаковые новые координаты | ровно один 201, остальные 409; в БД одни координаты |
| 4. Импорт | N пользователей одновременно импортируют файлы с общим именем | ровно один импорт успешен, остальные отклонены целиком |
| 5. Два администратора изменяют один объект | чётные потоки — администратор 1, нечётные — администратор 2; все меняют чужой объект по одной и той же версии | ровно один 200, остальные 409 (изменение по устаревшей версии); итог — значение успешного изменения, версия +1 |
| 6. Администраторы изменяют и удаляют один объект | администратор 1 удаляет, администратор 2 изменяет, все по одной версии | успешна ровно одна операция: удаление (204, остальные 404) или изменение (200, остальные 409); итог ей соответствует |
| 7. Удаление + привязка | один удаляет объект, остальные одновременно привязывают новые объекты к его координатам | без ошибок сервера; координаты остаются, если к ним успели привязаться, иначе удаляются |
| 8. Проверка | читает итоговое состояние БД через API | все инварианты выше соблюдены |

Каждый запрос проверяет код ответа: любой 5xx — провал. Группа 8 сверяет состояние БД
со счётчиками успешных ответов.

Изменение и удаление объекта передают версию, которую клиент видел (`"version"` в теле PUT,
`?version=` у DELETE), — так же, как это делает веб-интерфейс.

## Результаты

10 одновременных пользователей, текущий сценарий. Полные сводки — в `results/`. Прогоны «было» и
«эксперимент» сделаны на временных сборках, где в `TransactionRunner` вместо SERIALIZABLE задан другой
уровень; оптимистическая блокировка (см. ниже) в них уже есть.

| Группа | READ COMMITTED (было) | REPEATABLE READ (эксперимент) | SERIALIZABLE + повтор (стало) |
|---|---|---|---|
| 2. Одно имя | **10 объектов с одним именем** | **10 объектов** | 1 × 201, 9 × 409 |
| 3. Одни координаты | **10 одинаковых координат** | **10 одинаковых** | 1 × 201, 9 × 409 |
| 4. Импорт | **все 10 импортов успешны, 10 дублей** | **10 дублей** | 1 × 200, 9 × 400 |
| 5. Два админа меняют объект | 1 × 200, 9 × 409 | 1 × 200, 9 × 409 | 1 × 200, 9 × 409 |
| 6. Изменение + удаление | одна операция успешна | одна операция успешна | одна операция успешна |
| 7. Удаление + привязка | **HTTP 500: нарушение внешнего ключа** | **HTTP 500** | без ошибок |
| 1 | без ошибок | без ошибок | без ошибок |
| Провалено проверок | 5 | 5 | **0** (стабильно в нескольких прогонах, также при 20 потоках — `results/4-serializable-20-threads.txt`) |

До появления оптимистической блокировки группы 5 и 6 выглядели иначе: в READ COMMITTED все 5
одновременных удалений одного объекта отвечали 204, а при одновременном изменении все 10 запросов
получали 200 и итог был равен последнему из них — изменения остальных молча терялись (lost update).

### Почему возникали ошибки в READ COMMITTED

Каждая изменяющая операция принимает решение по прочитанному, а потом пишет:

- **создание, изменение, импорт** — «имя (координаты, локация) свободно» → INSERT/UPDATE;
- **удаление** — «объект существует» → DELETE, затем «координаты больше никем не используются» → DELETE координат;
- **изменение** — «объект существует» → UPDATE.

В READ COMMITTED каждый запрос видит только закоммиченные данные. Две параллельные транзакции
читают одно и то же «до», обе решают, что всё в порядке, и обе пишут:

- в группах 2–4 обе вставки проходят — уникальность нарушена;
- в группе 7 удаление не видит незакоммиченную привязку, удаляет координаты, и PostgreSQL
  отвергает это нарушением внешнего ключа, которое доходит до клиента как HTTP 500.

### Почему не REPEATABLE READ

В PostgreSQL REPEATABLE READ — это изоляция снимков. Она запрещает менять строку, которую
параллельно изменила или удалила другая транзакция. Но в группах 2–4 и 7 транзакции пишут
**разные** строки (две новые записи `person` с одинаковым именем). Это аномалия *write skew*:
снимки её не обнаруживают, и эксперимент это подтвердил. Обнаруживает её только SERIALIZABLE
(Serializable Snapshot Isolation): PostgreSQL отслеживает зависимости «прочитал → другой записал»
и откатывает одну из транзакций с ошибкой `40001`.

### Почему одного уровня изоляции мало для групп 5 и 6

Уровень изоляции действует внутри одной транзакции, а администратор читает объект (открывает форму)
в одном HTTP-запросе, а сохраняет — в другом, иногда через минуты. Между ними второй администратор
успевает сохранить свою правку, и транзакция первого, даже SERIALIZABLE, честно перезаписывает её:
с точки зрения БД это две последовательные транзакции, аномалии нет. Потерянное обновление здесь
возникает на уровне пользовательского сценария «прочитал → подумал → сохранил», и защищает от него
оптимистическая блокировка, а не уровень изоляции.

## Изменения и их обоснование

1. **Изменяющие операции выполняются в SERIALIZABLE**
   (`service/TransactionRunner.java`, вызовы в `PersonService`, `ImportService`, `AuthService`):
   создание, изменение, удаление, импорт и регистрация. Во всех них проверка
   «прочитал → записал» обеспечивает инвариант: уникальность, существование объекта,
   отсутствие зависимых объектов. Уровень задаётся первой командой транзакции
   (`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE`) и действует только до её конца.

2. **Чтение осталось в READ COMMITTED**: список, просмотр, специальные операции, история
   импорта. Они ничего не решают по прочитанному и не пишут, а более строгий уровень дал бы
   только лишние конфликты. Запись о неудачном импорте (`ImportService.recordFailure`) —
   одиночная вставка без проверок, поэтому тоже в READ COMMITTED.

3. **Автоматический повтор при конфликте сериализации.** Ошибка `40001` (и `40P01`, взаимная
   блокировка) — штатный результат SERIALIZABLE, а не сбой. Операция повторяется целиком в
   новой транзакции и уже видит результат конкурента: отвечает 409 «имя занято», 404 «объект
   удалён» и т. п. Задержка между попытками растёт экспоненциально со случайным разбросом, до
   20 попыток. Если конфликты не прекращаются, клиент получает 503 с просьбой повторить.
   На маленьких таблицах PostgreSQL ставит предикатную блокировку на всю таблицу, поэтому
   конфликтуют и операции над разными объектами (группа 1). Повтор делает такие ложные
   конфликты незаметными для пользователя: за прогон сервер поглощает десятки ошибок
   сериализации, а клиенты не получают ни одной ошибки.

4. **Оптимистическая блокировка объектов** (`@Version` в `Person`, колонка `person.version`).
   Клиент получает версию вместе с объектом и присылает её при изменении и удалении; если объект
   с тех пор изменил кто-то другой, сервер отвечает 409 и ничего не меняет, а веб-интерфейс
   предлагает загрузить актуальную версию. Без версии изменение и удаление отклоняются (400).
   Проверка версии идёт внутри той же SERIALIZABLE-транзакции, поэтому одновременные запросы с одной
   версией не проскакивают оба: второй получает ошибку сериализации, повторяется и видит новую версию.
   На случай, если UPDATE/DELETE по версии не затронет строку, `OptimisticLockException` тоже
   повторяется. Откат объекта администратором из журнала версию не требует: он явно применяет
   выбранное состояние к текущему объекту.

5. **Отключён разделяемый кэш EclipseLink** (`persistence.xml`, `shared-cache-mode=NONE`).
   Чтение из кэша не доходит до PostgreSQL, и SERIALIZABLE его не видит: `em.find()` мог вернуть
   объект, который другой пользователь уже удалил, и тогда изменение «удалённого» объекта
   молча проходило.

Ограничения уникальности по-прежнему проверяются только в бизнес-логике (требование ЛР2):
в БД нет ни UNIQUE-ограничений, ни уникальных индексов на эти поля. Корректность при
параллельной работе обеспечивает уровень изоляции, а не схема БД.

### Что осталось за рамками

- **Ожидание под нагрузкой.** При 20 одновременных пишущих пользователях отдельные запросы
  ждут повторов до 1–3 с. Это цена строгой изоляции на маленьких таблицах. Большой импорт
  (1000+ записей) при непрерывном параллельном создании объектов может исчерпать попытки и
  получить 503 — тогда ни один объект не создаётся, а операция попадает в историю как неудачная.
